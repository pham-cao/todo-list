# BUG-011: After Giữ lại on the task delete note, a quick Enter on Xóa reopens it and the late close event makes Xóa việc delete nothing

- Severity: Medium
- Priority: P3
- Status: Closed (Verified 2026-11-10)
- Found in: task-groups T9 attempt 3 (review and FE analysis); the code is from daily-task-log (shipped task delete note in src/app.js)
- Related TC: TC-task-groups-T9-27; requirements R51, R62 (task delete note behaviour of daily-task-log)

## Environment
Chromium (Playwright), desktop and phone projects, keyboard, tasks of any day.

## Steps to reproduce
1. Focus Xóa on a task row and press Enter. The note opens with Giữ lại focused.
2. Press Enter (Giữ lại), then Enter at once on the returned Xóa so the note opens again.
3. Press Xóa việc.

## Expected
The task is deleted.

## Actual
The close event of the first note arrives after the second opening and clears the pending delete, so Xóa việc closes the note and deletes nothing. FE measured 10 failures in 20 runs without the guard.

## Cause
The queued close event runs after the note was reopened and resets pendingDelete. The same race on the group notes was the blocker found on the BUG-009 path ("Xem các việc này" did nothing).

## Impact
A fast keyboard user sees the delete silently not happen. No data is lost.

## Fix and retest (2026-11-10)
FE: the shared close handler returns while a note is open again (and the card got the same guard). Retest: rapid keyboard bursts on the task delete note (8 cycles then Xóa việc) pass 5 of 5 on both projects, plus the FE regression test. I did not edit src, so I could not run a without-the-fix mutation; FE reports the test fails without the guard. Evidence: evidence/T9/rapid-probes.txt, full-suite-attempt3-repeat2.txt. Result: Verified, Closed.
